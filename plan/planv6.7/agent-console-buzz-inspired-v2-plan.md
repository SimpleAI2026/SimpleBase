# planv6.7 · 云助手协作群工作台 v2：群成员、多会话、路由分工与人工协作

> **状态：** 设计与实施计划，待实施；2026-11-21。
> **基于：** [v1 工作台计划](agent-console-buzz-inspired-plan.md)。涉及协作群的产品语义、路由、导航、归档及回退策略，以本文为准；不删除 v1，不将本计划当作已实现能力。
> **本次交付：** 仅编写计划，不修改前后端业务代码，不启动服务，不执行 `init_db`、DDL、reset 或运行库数据变更。
> **基线：** 当前工作区（含尚未提交的 v1、Plan 等改动），不是仅以 Git 已提交版本为准。下文区分“代码现状”和“v2 提案”。

## 0. 本轮必须纠正的产品模型

### 0.1 用户需求与确定决策

1. **Tag 就是协作群，不是问题分类，也不是助手切换器。** 群里可以有多个助手；人是同级协作参与者，但不是拥有模型、工具与 API Key 的 AI 助手资源。
2. **每个群有自己的路由提示词。** 每次会话发送、助手交接、人工回复都在该会话的上下文内做决策；路由器决定交给谁、做什么、依赖谁，而不只是选一个回答者。
3. **每个群有多个独立会话。** 普通问答、告警处理、统计分析、定时巡检都可以创建多条；不再只有 `#对话` 能展开会话，`#告警`、`#统计`、自定义群全部同构。
4. **显式 `@` 一个或多个助手，即为本轮执行目标。** 不换群、不换会话、不把多个助手压缩成一个；收到有效分派后自动开始可执行任务，依赖未满足的显示排队。
5. **需要人时，路由器或助手可请求 `@当前人`。** 在消息流中产生有对象、有说明、有状态的人工任务；人回复/完成后继续同一轮协作，不把“普通文本里提到你”当作任务实现。
6. **所有群旁都有 `+`。** 菜单明确提供“添加已有助手”“新建助手并加入”“新建会话”；群成员栏另有直接“添加助手”的 `+`。新建群表单也能连续添加/新建多个助手。

### 0.2 v1 哪些约定作废

- 作废“一轮只允许一个助手”“标签提示词仅作快捷输入”“点名只覆盖单回答者”“标签不展开二级会话”。
- 作废“群归档后把会话搬回公共对话并扩大助手候选”的处理方式。
- 作废“旧后端可以把新协作会话当普通未绑定会话继续写入”的回退假设。
- 保留项目权限边界、助手资源管理、旧会话历史、工具审批、运行取消、Plan 六阶段与 UI 组件规范。
- 现有 `prompts[]` 仍是快捷问题，不偷换数据含义。新增独立 `routing_prompt`；旧快捷问题可保留在折叠的“快捷问题”区，但不再作为群配置的核心。

### 0.3 范围与非目标

**v2 必须交付：** 群与多会话导航、群内增建助手、路由提示词、多助手分工、当前人待办及恢复、可追踪的路由消息、定时群会话、刷新恢复和兼容隔离。

**明确的实施选择：** 第一版多助手任务按依赖顺序串行执行；同一轮确实可以调用多个助手，不是“多选后只用一个”。这是保留工具审批与线程互斥的安全实现，不承诺并行首字输出。独立只读任务并行可后续扩展，不是本轮验收前提。

**不做：** 企业通讯录、任意用户邀请、私密群 ACL、跨项目协作、外部 IM 推送、无限助手互聊、通用工作流编辑器。告警类会话与已授权输入接入点属于本版；自动发现全部告警源、实时订阅平台不属于本版。

## 1. 现有代码核查与必须先修的偏差（AGC2-BASE）

以下为静态阅读结论，未执行接口、测试或真实模型验证。

- `ui/src/pages/AgentManager.vue`：已存在群标签相关页面状态和组件，但 `resetThread` 在标签有助手时传 `agentId + tagId`。`internal/api/agent_handler.go` 要求 `tag_id` 必须配 `dispatch_mode=auto`，同时禁止 `auto + agent_id`。**当前常见新建标签会话路径存在前后端契约冲突。** v2 编码前先补契约测试，不把现状复制进新群流程。
- `ui/src/components/agent/AgentWorkspaceSidebar.vue`：只有 `#对话` 有二级会话树及新建会话 `+`；其余标签没有同等导航能力。
- `AgentTagModal.vue` / `AgentRosterBar.vue`：已有多个项目助手选择与点名展示，但没有当前人身份、群内新建助手流程，也没有专用路由提示词。
- `ui/src/services/types.ts`：`AgentTag` 是 `agentIds + prompts`；mention 只有 `agent_id`；路由结果只有一个 `agentId`。`useAgentConversation.ts` 持有单个 `runId` / `confirmation`，不足以代表协作轮次。
- `internal/systemdb/agent_tags.go`：已有 tag、thread workspace、run route 三表；`dispatch_mode=auto` 的定义仍是一轮一助手。助手是项目级资源，不应改成只能属于一个群。
- `internal/api/agent_dispatch.go`：输入是正文、历史、候选助手，固定提示词输出单个 `agent_id`，没有读取群路由提示词。
- `internal/api/agent_run_handler.go`：多 mention 返回 `multiple_agents_not_supported`；旧固定助手会话继续返回 `agent_switch_required`。前端允许发送不代表服务端已经支持切换。
- `gocloudagent/cloudagent/run_types.go` / `runthread.go`：底层一次只运行一个 Agent，`ClaimThread` 对同一会话互斥。不能通过前端循环调用原 `CreateRun` 实现多助手协作。
- `internal/agentbridge/principal.go`：已有跨助手历史投影，可复用；`internal/api/run_events.go` 已有 run 级内存 SSE 回放，但不是持久任务队列。
- `internal/agentbridge/cron_agent.go`：定时任务直接运行固定助手，使用只读调度主体和 `Headless`，没有经过交互端自动路由。
- `internal/auth/principal.go`：登录态有 `UserID`，API Key 没有用户身份；旧 thread 的 `CreatedBy` 取 `APIKeyID`，不能用它识别当前人。
- `internal/systemdb/schema.go` 采用最终态 schema。遵循 `internal/AGENTS.md`，本方案不新建版本化迁移体系，不安排 `ALTER` 补列，更不自动 reset 用户运行库。

## 2. 领域模型：群、会话、轮次、任务分开（AGC2-MODEL）

### 2.1 核心对象

- **群 `AgentTag`：** 项目内的协作空间；保存群名、有序助手成员、路由提示词和路由配置版本。沿用 `/agent-tags`，避免新增一套同义 `groups` API。
- **成员 `Participant`：** `kind=agent|human` 与稳定实体 ID。AI 成员引用现有项目助手；当前人从认证主体解析，不伪造 `CloudAgent` 数据行。
- **会话 `AgentThread`：** 属于一个群，保存独立历史与参与人上下文。一个群可有任意多条分页会话；历史只在本会话中读取，不自动汇入全群历史。
- **轮次 `AgentTurn`：** 一次用户发送或一次定时触发形成一轮协作；用户消息只落一次。轮次保存路由决策、配置快照、任务列表、发起主体、状态、版本与预算。
- **任务 `AgentTask`：** 分派给一个成员的一项职责，拥有稳定 ID、依赖、尝试号与结果。助手任务关联一个或多个历史尝试 run；人工任务没有模型 run。
- **运行 `AgentRun`：** 保持现有“一个助手的一次执行尝试”语义，不用一个 `agent_id` 字段假装代表多个助手。
- **事件与消息：** 消息给人阅读，任务/轮次状态是执行权威。路由卡、人工卡从结构化记录生成，不从助手自然语言或前端气泡推断状态。

### 2.2 群与会话分类

群名与会话种类必须正交：`#告警` 默认新建告警会话，但用户也能在其中新建统计会话。

- `thread_kind`：`chat` / `alert` / `statistics` / `scheduled`，用于图标、默认表单和筛选，不代表不同执行权限。
- `source`：保留既有 `workspace` / `starter` / `bi` 来源口径；新群入口可扩展 `api` / `scheduler` / `event`，只用于可追踪来源。
- 定时统计允许 `thread_kind=statistics`、`source=scheduler`；不能用一个字段同时表达分类和触发方式。
- 新群会话使用 `dispatch_mode=collaborative`，不填 `agent_id`。保留 `auto` 与旧固定会话，不静默改写历史执行模式。
- `#对话` 在新 UI 是可配置的默认协作群，按项目解析默认助手；`chat` 从“仅虚拟分区”升级为可读默认值、首次显式写入时持久化的内置群。`alerts` / `stats` 沿用原 ID；增加定时内置群 `scheduled`，保留这些 ID/内置名称。
- 历史无群会话独立显示于“历史会话”入口；增加明确的列表 scope，不再用 `created_by=''` 猜测控制台归属，也不把 scheduler/BI 会话随意混入默认群。
- 内置群读取仍无写入副作用。兼容旧 `tag_id=chat` 的历史筛选：新端列表显式传 `workspace_version=2`，未传时保留旧语义。

### 2.3 当前人的身份规则

- 交互发送时，以 `Principal.UserID` 固定本轮 `human_participant`；发言人和任务接收人必须记录真实 UserID，UI 显示“你”只是本地化投影。
- 群启用“当前人参与”策略，不将每个打开群页面的访客自动持久化为成员。会话可展示其已实际参与的人员，默认新轮次仅路由给发起人。
- `@当前人` 在持久化前解析为本轮确定的用户；另一个人打开页面，不得把已有任务的接收人替换成自己。
- API Key 没有“当前人”，不得以 Key ID 冒充用户。需要人工时标记“缺少人工接收人”，不创建无人可处理的隐形任务。
- 定时任务必须显式配置仍有项目访问权的人工负责人；v2 默认只允许登录用户绑定自己。API Key 创建的任务不支持随意传 UserID 指派他人。
- 人工负责人在本版仅表示任务对象，不将其权限借给 scheduler。人回复后需在新的认证请求中显式选择“继续处理”，服务端重新校验权限，不能保存长期登录令牌用于恢复。

## 3. 前端信息架构与交互（AGC2-UI）

### 3.1 两栏群聊工作台

沿用左导航、右会话，不增加常驻第三栏。主区域按以下顺序排列：

1. **群/会话头：** 群名、会话标题、会话类型、群设置、新建会话。
2. **成员栏：** 当前人及群内多个助手的头像/名称，最后是“添加助手 `+`”。状态是“执行中 / 排队 / 等你处理”，不显示误导性的单一“当前助手”。
3. **消息流：** 用户消息 → 路由分工卡 → 各助手有身份的独立消息与工具卡 → 人工待办/回复 → 可选汇总。
4. **输入区：** 多目标 `@` chips、草稿、发送/停止、当前轮次状态；等待人时仍可输入指定待办的回复。

左栏每个群都可展开，下面列独立会话。例：`#告警` 下同时有“支付失败排查”“缓存异常”；`#统计` 下同时有“昨日订单”“周报”；自定义 `#发布检查` 下有“上线检查”“每日巡检”。不能只在概览里放“最近会话”来替代导航树。

### 3.2 `+` 的位置与动作

- **导航顶部 `+`：** 仅“新建协作群”，不立即发起对话。
- **每个群行 `+`：** 打开 `Popover` 菜单，依次为“添加已有助手”“新建助手并加入”“新建会话”；包括内置群，不仅自定义群。按钮名称为“向群添加…”，各菜单项有清晰语义。
- **成员栏 `+`：** 直接打开添加助手面板，分“选择已有”“新建助手”；支持已有助手多选，一次加入多个。
- **新建群表单：** 名称、成员、路由提示词；成员字段内同样有 `+`。创建群前的新助手先保留表单草稿，最终由服务端组合操作创建并加入，避免取消群表单时遗留一批助手。
- **会话列表/群概览：** 提供文字按钮“新建会话”，不要求用户猜 `+` 的作用。
- 点击群的 `+` 不切换当前会话、不触发发送；失败保留原选中态与表单。菜单和展开按钮必须是同级 DOM，不延续按钮嵌套按钮的结构。

“创建助手”和“加入已有助手”要分开：助手为项目资源，可以进入多个群；从群移除不等于删除项目助手。群设置内编辑的是成员关系；修改共享助手配置时提示会影响其他使用该助手的群。

### 3.3 群设置与路由提示词

`AgentTagModal.vue` 升级为群配置表单：成员选择是主要区块，其次为明确标注的“路由提示词”，而不是若干快捷问题按钮。

示例语义：数据库结构/订单分析交给数据库助手；文件核对交给对象存储助手；跨域任务拆分后先取数再核对；信息不足、需要线下动作或业务判断时交给当前人；完成后由指定成员汇总。

编辑器说明必须写清：提示词决定分工，不授予工具权限，不等于助手系统提示词；不填写密钥。提示词保存后仅影响新轮次，进行中的轮次显示其配置版本。未保存内容不参与路由，409 冲突保留草稿。

### 3.4 多会话与消息表现

- 每个群独立保存展开状态、分页 cursor、加载/错误态；切群不新建记录。搜索覆盖已加载群和会话标题，明确标识范围，不伪称全历史搜索。
- 新建会话先选择类型并进入草稿；首次发送或明确确认创建时才落库。定时会话使用专门配置表单，不在群名叫“定时”时自动启动调度。
- URL 继续以 `?tag=&thread=` 定位，`thread` 的服务端真实归属优先；可增加 `task` 定位人工卡。URL 不携带消息正文或路由提示词。
- 路由消息显示“路由协调 → @数据库：核对订单 → @对象存储：核对文件 → @你：确认异常”，并标注指定/自动/交接。路由器是系统身份，不伪装成通用助手发言，也不公开模型思维链。
- 两个助手输出必须有不同消息 ID、任务 ID 与实际发言者；不能合并进同一 assistant 占位气泡。工具与审批卡挂在对应子任务下。
- 人工卡显示任务、所需输入、接收人、发起者、依赖状态和“回复并继续 / 无法处理”；完成与回复是实际请求，不是本地打勾。待办数以服务端状态为准，不等于未读数。
- 汇总是明确分派的助手任务，会计费；不把“最后一个助手结束”伪装成所有任务完成。无需汇总时直接显示轮次结果摘要。
- 移动端复用同一侧栏放入 `Sheet`；成员栏折叠但保留 `+` 和待办计数。320px 下可展开群、点名多人、处理人工卡，无横向溢出。

### 3.5 前端状态与组件落点

- `AgentManager.vue`：仅保留项目、群、会话选择与布局装配，删除“选择助手即切会话”的新模式分支。
- `AgentWorkspaceSidebar.vue`：所有群统一树结构；每群分页和 `+` 菜单；历史会话单独入口。
- `AgentRosterBar.vue`：agent/human 联合参与者展示、任务状态、多选点名与添加成员事件。
- `AgentTagOverview.vue`：群说明、成员、路由规则摘要、多会话列表与新建入口；不再以快捷提示词为中心。
- `AgentTagModal.vue`、`AgentFormModal.vue`：群配置与复用的助手表单；新增业务级成员选择面板，不重建基础 `ui/` 组件。
- `AgentComposer.vue` / `AiChatComposer.vue`：结构化多目标 mention；候选严格为当前群助手与本轮可接收的当前人。发送不自动塞首个助手；只输入同名文字不产生结构化分派。
- `ConversationView.vue`：路由、分工、人工结果、多个执行者的消息展示；新增 `AgentDispatchCard.vue`、`AgentHumanTaskCard.vue` 作为建议落点。
- 新增 `useAgentWorkspace.ts` 负责群与会话导航；新增 `useAgentCollaboration.ts` 负责 turn/task/run 状态与事件归并。旧 `useAgentConversation.ts` 保留旧 run/Plan 路径，底层解析器可复用，不硬把一个 `runId` 扩成万能状态。
- 状态按 `projectId + threadId + turnId` 隔离，任务/审批按 `taskId + runId + callId` 索引；切项目后丢弃旧请求/事件，不能相互覆盖。
- `services/types.ts` 全部对象用 `interface`，新增字段经 `http-api-converters.ts` 映射 snake_case → camelCase，页面只调用 `api.*`。
- 草稿按项目/群/会话隔离，仅本地恢复输入；成员、路由、任务和权限不能以 localStorage 为事实来源。

## 4. 会话路由与多助手执行（AGC2-ROUTE）

### 4.1 一轮协作的处理顺序

1. 校验项目、实例写状态、会话模式、群是否归档、模型额度、发起主体；取得会话编排锁。
2. 按幂等键创建 turn，并在同一事务里记录一次用户消息及身份；固定群版本、成员与人工接收人快照。
3. 显式 `@` 时以结构化目标为准；无 `@` 时调用本会话路由器，读取群 `routing_prompt`、当前请求、有限历史与成员能力说明。
4. 校验结构化分工，持久化 route decision 与 task；先产生可见路由卡，再启动任务。失败不能留下一个没有解释的“运行中”气泡。
5. 按依赖顺序串行执行 ready 的助手任务；每项仍调用现有单助手 Runtime，分别记录 run、消息、工具、用量与审批。
6. 人工任务就绪后显示 `@用户` 待办；没有可执行助手任务时进入 `waiting_human` 并释放模型执行资源，不用模型循环等人。
7. 人工回复或受控交接触发继续推进；全部必要任务完成后结束轮次，汇总任务如存在也必须结束。

### 4.2 点名与自动路由的优先级

- **显式点名：** `mentions[]` 升级为 `{kind, id}`；同一成员去重，支持一个或多个 agent/human。旧 `{agent_id}` 仅在兼容接口中转换，不混用两套权威字段。
- 点名就是“请这些成员处理”，不是普通社交提及。所有有效目标必须成为任务；无依赖时按点名顺序执行，任务输入保留原始请求及本轮前序结果。
- 显式目标禁止被模型替换或静默增加执行者。需要更精细分工时路由器只可在显式目标集合内拆解；解析失败退回按点名顺序的确定性任务，不丢掉其中一个目标。
- **自动路由：** 可返回一个或多个任务及前置依赖，也可只交给当前人补信息。助手未被选中不执行，不做全群广播抢答。
- **助手交接：** 通过受控结构化协作输出请求 `request_handoff` / `request_human`；由宿主校验并提交任务，不靠扫描自然语言里的 `@`。交接对象限群内，自动路由轮次允许有界追加；显式点名轮次需要额外执行者时先请人同意，不能偷偷扩张目标。
- 群只剩人工成员时允许纯人工任务；群既无可用助手又无法解析人工接收人，返回可恢复配置错误，不回退到群外助手。

### 4.3 路由器契约与边界

输入：群路由提示词和版本、成员 ID/名称/职责/可用能力、当前消息、会话内有限上下文、已完成任务摘要、本轮人工身份。只使用稳定 ID，名称只供解释。

输出：`decision_id`、任务项（目标、目标说明、依赖 ID）、是否需要汇总、简短理由码。客户端展示的是结构化任务与简短说明，不保存/展示隐藏思维链。

- 路由调用不带工具，不查询数据库，不做写操作；群提示词是受限配置，不能覆盖身份、成员范围、审批与预算约束。
- 建议初始上限：每轮 8 个任务、最多 2 次追加交接、依赖深度 4、路由单次 8s、结构化输出最多 1,024 tokens；沿用项目总配额并逐次检查。具体常量集中定义，不散落 handler。
- 输入预算沿用有限历史投影；群路由提示词限制 4,000 字符，正文与成员简介分别截断。输入截断必须可测试，不把全群历史送入模型。
- 服务端校验成员归属、能力、重复任务、循环依赖、缺失依赖、人工对象和预算。任务 DAG 无效则整体不执行，不能一边校验一边产生副作用。
- 自动路由超时/越界/低置信度：仅可回退到群中显式配置且可用的 `fallback_agent_id`；未配置则请求当前人澄清，有效人工身份也没有时以 `routing_failed` 结束。**不沿用“随便取第一个助手”的不透明降级。**
- 日志仅记录 ID、计数、耗时、错误码、版本和哈希；用户内容和路由提示词不进日志/审计。业务会话存储与日志渠道分开，遵守既有脱敏策略。

### 4.4 线程锁、取消、重试与恢复

- **两级互斥：** 持久 `active_turn_id` 控制同一会话仅一轮协作；Runtime 执行锁控制当前子 run。等待人时释放 Runtime 锁但保留轮次占用。
- 同会话新问题在活动轮次未结束时返回 `409 turn_busy`，前端保留草稿并提示“回复当前待办或取消本轮”；不实现隐形无限队列。人工回复接口是续跑入口，不再走普通新轮次接口。
- 串行子 run 使用自身 run ID 依次 `ClaimThread/ReleaseThread`；无需伪造 ThreadID 或同时持有多个子 run。**所有入口**（旧 runs、Plan、cron、v2 turns）都需先检查持久轮次占用，不能只依赖内存锁。
- 停止整轮：取消路由 ctx、当前 run 与审批等待，未开始任务及人工任务标记 canceled，保留已完成结果；不回滚已经执行的工具副作用。
- 单任务重试只针对 failed/interrupted 的目标与依赖快照，新增 attempt/run，不重复落用户消息、不重跑成功兄弟任务、不重新随机选助手。失败依赖的下游保持 blocked。
- 群配置更改不改进行中任务分工；但每次执行前仍校验成员未被移除、助手未归档、访问权与实例状态。失效时暂停并提示调整，不偷偷换助手。
- 重启后，遗留路由/执行中的轮次及 run 收敛为 interrupted；人工等待任务可从持久状态恢复。未知结果的写操作绝不自动重试，不承诺 exactly-once。
- 人工回复与取消并发使用 `expected_version`；事务中检查活动轮次、任务状态、接收人、幂等键，成功一次才推进。

### 4.5 状态口径

- Turn：`routing`、`running`、`waiting_human`、`waiting_approval`、`completed`、`failed`、`canceled`、`interrupted`。
- Task：`pending`、`ready`、`running`、`waiting_human`、`waiting_approval`、`completed`、`failed`、`blocked`、`canceled`、`interrupted`。
- 状态新增在协作对象上，不直接改现有 `AgentRun` 枚举。旧 run 继续用现有状态，再由协调器投影到 task/turn。
- 非依赖任务可在另一个任务失败/等待人时继续；没有可运行任务且有失败依赖时轮次 failed，没有失败而仅待人时 waiting_human。仅必要任务全部完成才 completed；可选任务须记录显式跳过理由，不静默忽略失败。

## 5. 人工协作与工具审批不能混为一谈（AGC2-HUMAN）

- **人工任务：** 需要业务信息、线下处理、判断、补材料或人工结论；创建时明确问题、接收人、交付要求和后续任务。人可以回复或说明无法处理。
- **工具审批：** 是否允许某 run 的某条受控命令执行。继续使用 `AgentConfirmCard.vue` 和已有审批协议，不能通过“我完成了”人工回复直接放行工具。
- 人工回复只接受接收人本人，或现有项目管理规则允许的显式接管动作；接管需记录操作者，不冒充原接收人。具体管理判断复用现有权限接口，不直接比较权限 map。
- 人工操作要求项目可访问、实例 writable、正确身份与版本；回复本身可按既有对话的 `database:read` 权限口径处理，但不因此获得 `database:write`。审批仍要求其原有写权限与发起人/管理员校验。
- 权限撤销、用户不可用、群归档、任务过期均可阻止继续；任务卡给出明确状态。API Key 不得仅靠知道 task ID 完成人工任务。
- 人工文本作为用户数据进入后续投影，不提升为系统指令；不要要求用户把 API Key、密码粘贴进卡片。
- 定时只读轮次遇到写操作应阻塞或结束并提示人工另发已授权操作；人工补信息不会把原来的定时主体自动升级为可写。

## 6. 存储、API 与事件契约（AGC2-CONTRACT）

### 6.1 存储方案：复用原表，新增旁表，不改旧列

最终命名可在实现 PR 冻结，但职责不能合并丢失：

1. **现有 `sys_agent_workspace_tags.config_json`：** 增量保存 `schema_version=2`、`routing_prompt`、`fallback_agent_id`、`human_policy`；`agent_ids` 继续是 AI 成员唯一权威，`prompts` 保留旧值。使用现有 tag `version` 做整个群配置的乐观锁，不再复制一份成员列表。
2. **新增 `sys_agent_collaboration_threads`：** 项目/会话/群 ID、会话种类、协议版本、人工负责人、`active_turn_id`、版本与时间。与 thread/workspace 在同一事务创建；群归属必须一致，不允许分别更新两边。
3. **新增 `sys_agent_turns`：** 发起主体 kind/ID、thread/tag、幂等键、请求摘要哈希、群配置快照、route decision、状态、version、预算和错误码。路由配置快照是业务数据，不是日志。
4. **新增 `sys_agent_tasks`：** turn/目标 kind/ID、任务目标、依赖、状态、attempt、人工回复及版本；新增 `sys_agent_task_runs` 保存每次尝试与既有 run 的关联，不能覆盖旧 run ID 丢失重试历史。
5. **新增 `sys_agent_message_participants`：** 关联现有 message ID 与真实 speaker/turn/task、消息种类、结构化 mentions；原消息 role 保持兼容。路由、人类消息不塞进虚构的 `agent_id`。
6. **新增 `sys_agent_group_cron_bindings`：** 关联既有 cron job 与 tag、会话策略、会话类型、人工负责人、固定 thread（如有）、触发去重关联。既有 cron 表不补列。
7. **新增 `sys_agent_collaboration_events`：** 轮次内单调 seq、事件种类、关联实体 ID/版本；持久化状态变更事件，SSE 文本 delta 仍可内存传输。任务变更与事件同事务提交，刷新可从业务快照重建。

DuckLake 无 PK/UNIQUE，所有逻辑唯一性必须由单写 Store 的共享互斥 + 事务收口；**仅“先查再插”不足以处理并发**。覆盖 turn 幂等键、task/run 关联、人工回复、内置群首次保存与事件 seq；HTTP、cron、后台恢复必须共用同一写入入口。

助手“新建并加入”提供 Store 组合事务；已有助手先校验成员归属再 CAS 写配置。409 时回滚本次新建，避免半成功孤儿助手。若最终因既有架构只能分步实现，必须返回已建 ID 并提供“继续加入”，禁止重试时再建一份；不能把分步接口宣传成原子操作。

新增表纳入项目删除、会话软删除可见性与既有数据保留策略；删除助手只影响未来执行，历史消息保留名称快照。新增表通过最终态 `schema.go` 描述；不修改用户数据库或引入通用迁移框架。

### 6.2 API 增量提案

以下均在 `/v1/projects/:projectID` 下，必须经项目上下文；新接口必须进入路由权限对账测试。

- `GET /agent-workspace-capabilities`：只读返回支持的协议版本、协作能力、限制和 schema 就绪状态。前端不得仅凭 tag 接口存在就认为支持多助手。
- `GET/POST/PATCH /agent-tags`：新增群配置 DTO；写请求附协议版本，更新附 `expected_version`。创建可带多个新助手草稿与已有助手 ID，由服务端原子创建。
- `POST /agent-tags/:tagID/members`：增加多个已有助手或创建并加入新助手，附 `expected_version`；`DELETE .../members/:agentID` 仅移出本群，不删助手。
- `POST /agent-threads`：新增 `dispatch_mode=collaborative`、`thread_kind`、`tag_id`；禁止 `agent_id`。`GET` 列表新增 v2 scope、类型过滤及每群 keyset 分页；过滤必须先于分页。
- `POST /agent-threads/:threadID/turns`：正文、结构化 `mentions`、`idempotency_key`；服务端返回 202 与 turn 快照。相同键相同输入返回原结果，不同输入返回 409；正文不作为日志去重键。
- `GET /agent-threads/:threadID/turns` 与 `GET /agent-turns/:turnID`：轮次列表/完整快照，包括 task、关联 run、待处理审批定位信息和 `last_event_seq`。
- `GET /agent-turns/:turnID/events?after=`：轮次状态事件 + 当前子 run 流；不存在的项目/会话/轮次组合不泄漏信息。
- `POST /agent-turns/:turnID/actions`：`cancel` / `retry_task` / `resume`，带目标、`expected_version` 与幂等键；resume 只推进可执行任务，不复用过期身份。
- `POST /agent-tasks/:taskID/replies`：人工正文与 `complete|unable`，附 `expected_version` 和幂等键，服务端解析提交人身份；可显式要求继续执行。
- `GET /agent-human-tasks?assignee=me&status=pending`：仅投影当前认证用户有权看到的任务，给群/会话待办计数与定位使用，不暴露全站人员。
- 既有 `/cron-jobs` 增加 `target=agent_group` 与群配置字段；既有 `function|agent` 不变。审批继续走既有 confirm 路由，需校验 task/run/turn 关联。

权限：群/成员/会话/定时配置修改沿用 `database:write`；读取用 `database:read`。创建/继续 turn 沿用现有 run 的读取权限口径并挂 `writeGate`，实际工具仍逐项授权；cancel/retry 校验发起人或合法管理员。所有新增写路径拒绝系统项目，缺失编排/策略依赖时 fail-closed。

错误码建议：`workspace_upgrade_required`、`group_archived`、`group_member_unavailable`、`turn_busy`、`turn_conflict`、`routing_failed`、`invalid_dispatch_graph`、`human_assignee_required`、`human_task_forbidden`、`task_not_retryable`、`collaboration_budget_exceeded`。统一领域错误映射，不以裸错误变成 500。

### 6.3 SSE 与刷新恢复

- 状态事件携带 `protocol_version`、`project_id`、`thread_id`、`turn_id`、`event_seq`，任务事件另带 `task_id`，执行事件另带 `run_id`、`agent_id`；人工事件带真实 participant ID。
- 事件种类至少含 `turn_created`、`route_decided`、`task_updated`、`human_requested`、`human_replied`、`turn_finished`。现有 run 的 token/tool/confirmation 帧封装在明确的任务上下文中，不共用一个全局 assistant 缓冲。
- 状态 SSE 是持久事件的投影；delta 只是流式体验，未承诺逐 token 持久回放。消息完成后以落库消息 ID 替换本地占位。
- 先取一致快照及 seq，再订阅 seq 后事件；去重按 turn/seq，delta 按 run/既有事件序号。迟到事件不能回退实体版本。
- `stream_gap` 或进程重启时刷新快照/消息并重连；不能把重连实现成重新提交 prompt。浏览器关闭不自动取消服务端轮次。

## 7. 定时、告警与统计会话（AGC2-SOURCE）

- **普通会话：** 手工创建，多助手路由按群规则执行。
- **告警会话：** 可以手工建立不同事件的处理会话；已授权 API 输入可指定 `thread_kind=alert`、外部事件 ID 并进入同一 turn 服务。先支持显式提交，不宣称已接实时监控订阅。
- **统计会话：** 多条独立分析主题；可手动触发或绑定定时任务，图表/报告是会话产物，不自动变成 BI 页面权限入口。
- **定时群会话：** 复用 `internal/cronjob`，新增群目标适配器调用相同协作服务；不在 Vue、API handler 内再造计时器。

调度绑定明确选择：

1. `reuse_thread`：每个任务绑定一条固定群会话，历次触发产生不同 turn，适合日报连续记录。
2. `new_thread_per_fire`：每次实际调度触发新建一条群会话，适合每次独立巡检；由 cron 执行实例 ID（或 job ID + 服务端计划时间）去重，同一触发重试不得重复建会话。

一次群可以绑定多条定时任务，两种策略都不会覆盖其他会话。绑定的固定 thread 被归档/丢失时暂停并提示重新选择，不能静默建到群外。群归档也暂停新触发。

调度器执行结果区分“本次触发已提交轮次”和“轮次最终完成”；保存 cron run → turn 关联，不把 202 当成统计报告已完成。超时、线程忙、额度不足记录稳定原因；有界重试使用同一触发键，不无限积压。

无人值守继续沿用只读 `Headless` 主体。路由提示词不得提高权限；需要人工时持久化负责人任务并结束本次调度占用，不阻塞 scheduler worker 等人。后续任务未完成不能被下一次触发覆盖。

## 8. 后端分层与逐文件实施落点（AGC2-BE）

### 8.1 共享编排入口

- `internal/api` 只做鉴权、DTO、HTTP/SSE、错误映射；交互路由与 cron 必须共享服务接口，不让 `agentbridge` 反向 import `api`。
- **宿主协作服务建议放 `internal/agentbridge`**：管理 turn/task 持久生命周期、身份重校验、单助手调用、人工恢复、事件发布和取消。通过注入接口接入现有 SSE/审批服务；不得复制另一套工具审批或命令策略。
- **纯协作规则放 `gocloudagent/cloudagent` 内**：路由输入/结构化输出、图校验、任务状态归约和预算检查；不读取宿主系统库，不 import 根模块。不新增平级“通用 agent”包。
- `internal/app` 为唯一装配点，创建同一个协作服务实例供 API 与 `CronAgentExecutor` 使用，关机停止接收任务、取消执行并收敛状态，失败路径反向释放。
- 旧 Plan 协调器仍按其既有接口工作；可将必要的 run 事件/审批执行器抽成注入能力，但不为 v2 顺手全面搬迁 Plan。

### 8.2 文件职责清单

- `internal/systemdb/schema.go`、`store.go`：旁表、共享锁、事务入口与 schema 检查；新增 `agent_collaboration*.go` 分别承载轮次、任务、事件与 cron 绑定仓储，避免把全部内容堆回 `agents.go`。
- `internal/systemdb/agent_tags.go`：新群配置、内置群、成员事务、v2 归档；`agents.go`：创建事务、列表过滤、旧/新 thread DTO 所需查询。
- `internal/api/agent_tag_handler.go`、`agent_handler.go`：群成员与会话新契约；`agent_run_handler.go`：拒绝把 collaborative 会话交给旧单 run 入口。
- `internal/api/agent_dispatch.go`：将可复用分类逻辑移交注入的路由服务，保留 v1 adapter；新增 `agent_turn_handler.go` / `agent_task_handler.go` 处理新 API，不把整个协调器写进 handler。
- `internal/api/run_events.go`：复用事件解析/审批能力，新增 turn SSE 适配；完整验证管理员审批与底层 hub 发起人校验一致，不能只测 handler。
- `internal/api/router.go`、`error.go`、Dependencies 定义及 adapter：新增权限、写门禁、系统项目拒绝、能力接口与领域错误。
- `internal/agentbridge/principal.go`：人工/系统/其他助手消息投影；只保留本助手合法工具消息，其他助手工具变摘要，不让新助手模仿不在其工具集中的调用。
- `internal/agentbridge/cron_agent.go`：保留旧单助手执行，增加调用共享协作服务的群目标分支；`internal/cronjob` 增加接口/结果关联，保持调度引擎唯一。
- `gocloudagent/cloudagent/run_types.go`、`runthread.go`：尽量保留单 run 契约，只增加受控协作输出和必要关联字段；串行调度不需放开 thread 互斥。
- `internal/app/assemble_agent.go`、启动/关闭装配：能力探测、共享服务、后台推进、遗留 running 收敛；不在 GET 请求里做初始化。

>
> - 协调器实际落在 `internal/api/collab_coordinator.go` / `collab_handler.go` / `agent_group_handler.go`：
>   轮次需要 run 行、消息、审批与 SSE 缓存，把它们搬进 `agentbridge` 属于大面积重构。
>   `agentbridge` 只声明窄接口 `GroupCronRunner`，由 `app` 注入 `api.GroupCronRunner` 后在 router 装配时 `Attach`，
>   依赖方向不变（`api` → `agentbridge`）。
> - 纯规则集中在 `gocloudagent/cloudagent/collab_plan.go`（解析、图校验、提示词拼装、状态归约、`NextTaskIndex`/`BlockedTasks`）。
> - 路由契约从「单 agent_id」扩展为 `RoutePlan`（返回原始 JSON），`Route`（单目标）保留给 `/runs` 兼容路径。
> - 权限口径：发起一轮与创建 run 一致（`DatabaseRead + writeGate`）；取消/重试/回复他人工单在 handler 内再校验主体。
> - 群归档改为**保留**会话 `tag_id`（原 §9.2 的「清空」未采纳），归档同时暂停该群定时绑定。

## 9. 兼容、归档与数据库发布边界（AGC2-COMPAT）

### 9.1 历史与模式隔离

- v1 `auto` 与旧固定助手会话照常读取/执行；新群会话才使用 `collaborative`。历史消息不重写，不猜测原本缺失的人工身份。
- 不批量把旧会话转成协作会话；可提供“在此群新建协作会话”，保留旧会话链接。后续需要历史转换应另做显式预检，不在首版偷偷迁移。
- v2 群写入后，v1 配置写请求若缺协议版本应拒绝或只允许严格的兼容字段更新，不能覆盖丢失 `routing_prompt`。初期采用拒绝并提示升级，简单且可测。
- 旧 `/runs` 访问协作会话必须返回 `workspace_upgrade_required`；不能忽略旁表后按通用助手执行。
- `?thread=` 旧链接可访问历史；旧 SDK 接口不变。新端连旧后端只展示旧能力，不露出无法执行的多点名/人工卡控件。

### 9.2 群归档

v2 群归档保留所有 thread 的群归属、成员快照和历史；不清空 `tag_id`，不移回默认群，不扩大路由范围。预置群不可归档；自定义群归档前展示影响范围。

有活动轮次/人工待办时，先提示用户完成或显式取消；归档事务再次确认不存在未终结轮次，同时暂停群关联调度，禁止新发送。前端不能只隐藏群当作停止执行。历史可从归档入口只读访问；恢复另作显式动作并重校验成员和调度，不自动恢复所有定时任务。

### 9.3 Schema 与发布

- 本设计尽量只新增旁表、扩展已有 JSON 与字符串枚举，避免改旧列。新表纳入 `schema.go` 最终态定义；若实施发现必须改旧表，先调整方案或取得用户明确授权，不能暗加 `ALTER` 或 reset。
- 发布前用只读 schema 状态检查确认表是否齐全；不齐全时禁用协作写入口并返回可操作错误，不默默降级成旧 run。
- 数据库初始化由用户手动执行，或由用户明确以正常服务启动流程触发；**代理不替用户执行 `init_db`/DDL。** 在 `TIMER_NO_RUN=1` 等跳过初始化的部署里，新增表不会凭空出现，必须在发布说明中明确预备步骤。
- 业务数据不做 GET 时懒写。默认群读取只返回虚拟默认配置，首次显式创建/更新时写入；历史会话不批量 backfill。
- 回退前停止新协作入口、暂停群定时、结束/中断执行并保留全部数据。旧二进制无法理解协作模式时，必须保留能拒绝新模式写入的兼容后端，或将相关访问置只读；**不能直接回退后继续写新会话。**

### 9.4 与 Plan、BI、starter 的关系

- 六阶段 Plan 是另一种显式执行协议，不能把一轮群聊的多助手任务等同于 Plan 阶段。
- v2 首版不在 collaborative 会话里启动 Plan；保留清晰入口“新建 Plan 会话”，并保留原会话。UI 与 API 同时拦截混用，避免两个协调器抢同一 thread。
- 已有 Plan、BI、首页 starter 按原绑定与 source 运行；需要项目助手并不等于自动进入某个群。其历史、审批、输出和深链均列入回归测试。

## 10. 实施顺序与阶段出口（AGC2-DELIVERY）

所有项均为待办；分 PR 不等于可以把不完整协作 UI 上线。

1. **PR0 · 基线契约与测试：** 修复标签新建会话参数冲突、mention 候选泄漏、固定会话测试与后端冲突；补真实 DTO/handler 契约用例。不得在这个阶段宣称支持群协作。
2. **PR1 · 模型与存储：** 冻结群、participant、thread/turn/task/事件契约；实现旁表、原子新建助手并入群、版本冲突、幂等事务、只读能力探测。测试使用隔离临时库/fake，不动用户运行库。
3. **PR2 · 后端协作核心：** 共享路由服务、有界多任务串行调度、历史投影、状态持久化、单助手 run/审批复用、取消与重启收敛。通过 fake 模型验证真正调用多个助手。
4. **PR3 · 人工闭环：** UserID 身份、人工待办/回复/续跑、权限与并发、拒绝/失效状态。此阶段结束才具备人机协作闭环。
5. **PR4 · 前端群工作台：** 全群树、所有群的 `+`、成员管理与路由提示词、多会话类型；可与 PR2/3 的已冻结契约并行开发，但未就绪能力不对用户开放。
6. **PR5 · 消息与运行交互：** 多目标点名、路由卡、多助手消息、人工卡、任务级进度/审批/停止/重试、SSE 重连与待办定位。
7. **PR6 · 定时与输入适配：** 群 cron target、复用/每次新建策略、触发去重、负责人和只读执行；告警/统计类型输入共用 turn 服务，不另建运行链。
8. **PR7 · 整体验收与发布：** 新旧模式隔离、历史/Plan/BI/starter、schema 未就绪、回退保护、真实 UI、权限与耗用边界；更新使用文档和必要项目规范后发布。

**v2 完成定义：** PR1–PR7 的必要路径连通，多助手与人工、多个群会话及定时路径都能被真实接口验证；只修改侧栏或渲染多个头像不算完成。并行执行、外部告警自动订阅与全员通讯录是后续扩展，不阻塞本版。

## 11. 验收与测试清单（AGC2-TEST）

### 11.1 用户场景验收

- [ ] 新建 `#发布检查`，从表单加入两个已有助手，再连续新建两个助手；刷新后仍在群里，取消创建群不遗留草稿助手。
- [ ] `#对话`、`#告警`、`#统计`、`#定时` 和自定义群都能展开并有 `+`；加入助手、新建助手和新建会话三个动作不会混淆。
- [ ] 同一群创建两条告警、两条统计和两条普通会话；历史互不串流，群成员与路由规则共享，切会话不新增记录。
- [ ] 不点名发送跨领域问题，路由产生数据库/对象存储两项任务，依赖顺序正确，两个助手真的执行并独立发言；线程 ID 不变。
- [ ] 显式 `@数据库 @对象存储`，两个目标均执行；不返回 `multiple_agents_not_supported`，不切换到两个私聊，不静默只用首个助手。
- [ ] 助手发现缺少业务确认后请求 `@当前人`，产生任务卡；本人回复后只恢复依赖该结果的任务，不重跑已成功助手。
- [ ] 刷新、关页重进、换浏览器打开同一会话，路由结果、任务状态、人工待办与发言者仍一致；另一个账号不能成为旧任务里的“当前人”。
- [ ] 同群创建两条定时任务，分别复用会话与每次新建会话；重复投递不重复创建 turn/thread，结果都位于该群而非旧助手私聊。
- [ ] 人工回复不会批准工具写操作；自动选中可写助手也仍需原有审批，定时主体不提升为可写。
- [ ] 群归档不搬走会话、不扩大候选；有待办/运行时有明确阻止与取消流程。旧固定会话、Plan、BI、starter 可继续使用。
